Project Access Control

Defines who can view and modify specific Projects (boards/tasks) within a Space. Projects may inherit from Space or apply project-specific roles.

Overview

  • Goal: Control access to project content (boards, tasks, views) for specified users within a Space.
  • Scope: Project is a sub-boundary of a Space; project permissions may inherit from or override Space roles.
  • Roles: Owner, Member, Guest; map to read/write/admin capabilities on project resources.
  • Invitation model: Invitations use an invitation_id (UUID); acceptance requires authenticated email to match the invite.
  • Security: Only project members can access project resources even if the Space is shared; stricter actions require higher roles.
  • Auditing: Track invites, acceptances, role updates, and removals for traceability.
  • Non-goals: Public (unauthenticated) read access to projects is out of scope.

APIs

  • Add/list/update/remove project members; manage invitations; list invitations.

OpenAPI & responses:

  • When project_acl is enabled, Project list/detail responses include user_role for the requester (nullable when disabled).
  • Register DTO schemas and paths in src/openapi.rs guarded by the project_acl feature.

Endpoint inventory (from appflowy-backend/doc/PROJECT_MEMBER_REQUIREMENTS.md):

  • POST /api/projects/{project_id}/members — Invite project member
  • GET /api/projects/{project_id}/members — List project members
  • PATCH /api/projects/{project_id}/members/{member_id} — Update member (role)
  • DELETE /api/projects/{project_id}/members/{member_id} — Remove member
  • POST /api/projects/{project_id}/invitations — Accept invitation (body carries invitation id)
  • GET /api/projects/{project_id}/invitations — List invitations
  • DELETE /api/projects/{project_id}/invitations/{invite_id} — Decline invitation

DTOs (planned; mirror Space): ProjectMemberModel, ProjectMemberInvitationPayload, ProjectMemberChangeset, ProjectInvitationModel, ProjectInvitationAcceptPayload, ProjectInvitationListQuery (see libs/shared-entity/src/dto/project_member_dto.rs in plan).

Notifications:

  • Project invite email sent on successful invitation (mailer template and registration under src/mailer.rs).

Example payloads (illustrative):

// Invite member to project
POST /api/projects/{project_id}/members
{
  "email": "dev@example.com",
  "role": "Member"
}

// Accept invitation
POST /api/projects/{project_id}/invitations
{ "id": "1f1a9c55-2cc0-4e3b-9a4c-2c1b3e1ad222" }

// Update role
PATCH /api/projects/{project_id}/members/{member_id}
{ "role": "Owner" }

Responses use the standard envelope (code/message/data). When enabled, project list/detail APIs include user_role for the requester.

Enforcement

  • Service-level authorization on all Project resources (boards/tasks).
  • Query filters to ensure only permitted projects/items are returned.
  • Project ACL plugin provides role/action threshold enforcement; Owner-only for sensitive operations (invite, role updates, removals), Member+ for listing.
  • Accept invitation: invitee-only; email must match pending invitation; idempotent on repeated accept.

Related backend/analysis: appflowy-backend/doc/PROJECT_MEMBER_REQUIREMENTS.md, Space ACL patterns in src/plugin/space_acl.rs.

Performance & Gating

  • Bulk role retrieval via Project ACL provider to avoid N+1 in project listing.
  • DB-level LEFT JOIN can emit user_role in list/detail when feature + runtime flag are enabled.
  • Runtime gating: return 404 for project member endpoints when config.addon.project_acl_enabled is false.

Planned Enhancements

  • Auto-assign the project creator as Owner on project creation when Project ACL is enabled (feature + runtime flag).

Role vs Action Matrix

Derived from appflowy-backend/src/plugin/project_acl.rs (ProjectAclPlugin::required_role_for_action).

Action Required Role Notes
Read Guest Read-only access to project resources.
Write Member Create/update items such as tasks, columns, views.
Delete Owner Delete destructive operations and administrative actions.

Roles reference: database_entity::dto::AFRole with ordering Owner > Member > Guest.
