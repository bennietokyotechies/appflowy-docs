Space Access Control

Controls visibility and permissions at the Space level. Spaces can be private or shared within a workspace and can contain multiple projects/boards.

Overview

  • Goal: Provide controlled sharing of a Space to specific workspace members with role-based capabilities.
  • Visibility: Spaces can be private (members only) or shared; discovery still requires workspace membership.
  • Roles: Owner, Member, Guest; define who can read, write, and administer a Space.
  • Invitation model: Invitations carry an invitation_id (UUID); acceptance requires the authenticated user's email to match.
  • Inheritance: Space roles may influence Project access; Space is the primary boundary for content grouping.
  • Auditing: Track invitations, membership changes, and visibility toggles for compliance.
  • Non-goals: Public (unauthenticated) access to Spaces is not supported.

Backend

Data Model

  • Tables: space, space_member, space_role, optional share_link. (TODO: ERD)
  • Indexes for permission checks on list/read queries.

APIs

  • Add/list/update/remove members, manage invitations, and list invitations.
  • Server handlers: see appflowy-backend/src/api/space.rs (feature-gated by space_acl and runtime SPACE_ACL_ENABLED=true).

Endpoint inventory (from src/api/space.rs):

  • POST /api/space/{space_id}/members — Invite space member
  • GET /api/space/{space_id}/members — List space members
  • PATCH /api/space/{space_id}/members/{member_id} — Update member (e.g., role)
  • DELETE /api/space/{space_id}/members/{member_id} — Remove member
  • GET /api/space/{space_id}/invitations — List invitations (supports query via SpaceInvitationListQuery)
  • POST /api/space/{space_id}/invitations — Accept invitation (body carries invitation id)
  • DELETE /api/space/{space_id}/invitations/{invite_id} — Decline/cancel invitation

DTOs referenced (see shared_entity::dto::space_dto): SpaceMemberInvitationPayload, SpaceMemberChangeset, SpaceMemberModel, SpaceInvitationModel, SpaceInvitationAcceptPayload, SpaceInvitationListQuery.

Example payloads (illustrative):

// Invite member
POST /api/space/{space_id}/members
{
  "email": "teammate@example.com",
  "role": "Member"
}

// Accept invitation (within workspace/space context)
POST /api/space/{space_id}/invitations
{
  "id": "9d1b0d5a-1b57-4a9e-a2e0-2c9a9f42a111"
}

// Update member
PATCH /api/space/{space_id}/members/{member_id}
{
  "role": "Owner"
}

Responses follow the standard envelope in appflowy-backend/API_ENDPOINTS_DOCUMENTATION.md with code, message, and data.

Enforcement

  • Handlers must filter spaces by user permissions for list/read; verify role on write.
  • Row-level constraints and service-level authorization checks.

Role vs Action Matrix

Derived from appflowy-backend/src/plugin/space_acl.rs (see InMemorySpaceAccessControl::required_role_for_action and SpaceAclPlugin::enforce_space_access).

Action Required Role (baseline) Public Space nuance Private Space nuance
Read Guest Requires workspace membership; non-members cannot read public spaces. Requires any space role (Guest/Member/Owner); non-members cannot read.
Write Member Must be a space Member or Owner. Must be a space Member or Owner.
Delete Owner Only space Owner. Only space Owner.
