In-App Notifications

Real-time notifications delivered within the product UI. This page documents the planned design, APIs, and frontend building blocks.

Business Overview

  • Purpose: Inform users immediately during active sessions without relying on email.
  • Scope: Mentions, invites, role changes, approvals, and system alerts.
  • Preferences (planned): Per-type/channel toggles, batching, quiet hours.

Status

  • Backend transport: WebSocket infra exists; events fan-out via Postgres LISTEN/NOTIFY.
  • Persistence: Planned table for durable notifications and read/unread.
  • APIs: Planned endpoints for fetching and updating read state and preferences.
  • Frontend: Toast utility exists for ephemeral messages; dedicated in-app UI to be implemented.

Architecture

Component — In-App Delivery

Sequence — Real-time Mention

Planned APIs

  • GET /api/user/notifications — list notifications (filter by read/unread, type, since)
  • PUT /api/user/notifications/{id}/read — mark a notification as read
  • PUT /api/user/notifications/read-all — mark all as read
  • GET/PUT /api/user/notification-preferences — get/update channel and per-type preferences

Frontend

  • Toast utility: appflowy-frontend/src/components/_shared/notify/index.ts for ephemeral feedback.
  • Notification Center: planned page/drawer for listing, filtering, marking read/unread.
  • WebSocket client: subscribe to workspace/user channels and dispatch UI updates.

Testing

  • Contract tests for WS payload structure and type safety.
  • API tests for list and read/unread semantics.
  • UI tests for badge counts, filters, and interaction flows.

Troubleshooting

  • WS not connecting: verify endpoint and auth tokens; check server logs.
  • Missing notifications: confirm DB persistence toggles and LISTEN/NOTIFY permissions.
